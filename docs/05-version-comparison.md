# 05 · 版本对照：v1 → v2

> 本文逐项对照两个版本的差异，说明"改了什么、为什么改、用户能感知到什么变化"。

---

## 一、演进动机

v1 是课程综合设计的提交稿：能完成全部基本要求，但作为工程作品有三类硬伤。

| 类别 | 问题 |
|---|---|
| **数据结构** | 全程 `std::vector` + `for` 循环线性查找。数据结构课设里没有任何真实数据结构，这是最尴尬的一点 |
| **能力缺失** | 无排序、无区间检索、无模糊搜索、无低库存告警——不是"没优化"，是"没有这个功能" |
| **工程缺陷** | 输入非数字崩溃、文件格式不可移植、中文环境多处失效、零测试 |

v2 的重构目标不是"加功能"，而是：**在完全相同的业务语义下，把每条访问路径换成复杂度最优的结构，并把收益量化。**

## 二、代码规模与组织

| 维度 | v1 | v2 |
|---|---|---|
| 文件数 | 1 个 `.cpp` | 12 头文件 + 5 源文件 + 1 测试 + 1 基准 |
| 代码行数 | 740 | 4,274（含测试 671 行、基准 396 行） |
| 组织方式 | 单文件顺序堆叠函数 | 三层分层 + header-only 模板库 |
| 构建 | 手工配置 VS 工程 | `run.bat` 一键 / CMake |
| 依赖 | 仅 Win32 SDK | 仅 Win32 SDK（**零第三方**） |

| `main()` | `src/main.cpp` |

## 三、数据结构对照

| 能力 | v1 | v2 |
|---|---|---|
| 主索引 | `vector<Item>` 线性扫描 | `HashTable<int, Item>` 链地址法 |
| 判重 | 遍历全部记录 | 哈希 `contains` |
| 按价格排序 | 不支持 | `AVLTree<double,int>` 中序遍历 |
| 按库存排序 | 不支持 | `AVLTree<int,int>` 中序遍历 |
| 价格区间查询 | 不支持 | AVL 范围查询 |
| 低库存告警 | 不支持 | AVL 范围查询 `[0, threshold]` |
| 按编号/名称排序 | 不支持 | 手写快排 / 归并（排下标） |
| 名称搜索 | 精确相等 | KMP 模糊匹配（大小写不敏感） |
| 日志容器 | `vector<History>` | `DoublyLinkedList<HistoryEntry>` + 容量上限 |

## 四、复杂度对照

| 操作 | v1 | v2 | 提升 |
|---|---|---|---|
| 按编号查询 | `O(n)` | `O(1)` | 哈希 |
| 按编号判重（新增时） | `O(n)` | `O(1)` | 哈希 |
| 新增（含判重） | `O(n)` | `O(1)` + 两次 `O(log n)` | — |
| 修改 | `O(n)` 查找 + 索引无 | `O(1)` + 两次 `O(log n)` | — |
| 删除 | `O(n)` | `O(1)` + 两次 `O(log n)` | — |
| 按价格/库存排序 | 不支持 | `O(n)`（中序） | — |
| 按编号/名称排序 | 不支持 | `O(n log n)` | — |
| 价格区间查询 | 不支持 | `O(log n + k)` | — |
| 低库存告警 | 不支持 | `O(log n + k)` | — |
| 名称精确查找 | `O(n·m)` | — | 被模糊搜索取代 |
| 名称模糊搜索 | 不支持 | `O(N·m)`（KMP 加速常数） | — |
| 日志追加 | 均摊 `O(1)`，扩容时 `O(n)` | 稳定 `O(1)` | — |
| 全量落盘 | 每次写操作都做 | 由调用方决定时机 | 批量导入从 `O(n²)` 降到 `O(n)` |

## 六、功能对照

### 保留（语义不变）

- 商品增删改查
- 按编号 / 按名称查找
- 操作日志记录与展示
- CSV 导入导出
- 彩色控制台菜单
- 二进制持久化（`warehouse.dat` / `history.dat`）

### 新增

- 按 4 个字段排序，支持升序 / 降序
- 价格区间查询
- 低库存告警
- 名称模糊搜索
- 索引诊断页（桶数、最长链、AVL 高度、一致性自检）
- 导入冲突策略（覆盖 / 跳过 / 取消）
- 单元测试与性能基准

### 修复

| 缺陷 | v1 表现 | v2 处理 |
|---|---|---|
| 输入非数字 | 菜单无限刷屏 | 全量校验 + 重试 + EOF 优雅退出 |
| 文件格式 | `sizeof(size_t)` → 32/64 位不通 | 定宽 `int32/uint32/double` |
| 写入中断 | 数据文件损坏，全部丢失 | 临时文件原子替换 |
| 文件截断 | 读到垃圾数据 | 尾部 `END!` 校验标记 |
| 旧数据迁移 | 无 | 兼容读取 WHv1 并自动回写 |
| 中文表格 | `setw` 按字节补齐，必然错位 | 按 Unicode 显示列宽补齐 |
| 中文路径 | `ifstream` 静默失败 | 宽字符路径 |
| 日志丢失 | 仅退出时保存，异常退出全丢 | 每次成功操作后落盘 |
| 数据目录 | 相对路径，双击与命令行各一份数据 | 以可执行文件所在目录为准 |
| 逐条落盘 | 每次操作全量序列化 | 调用方择机 flush，批量导入只写一次 |

## 七、用户可感知的行为差异

| 场景 | v1 | v2 |
|---|---|---|
| 菜单编号 | 1~9 | 0~11（0 = 退出） |
| 退出键 | 9 | 0 |
| 日志条数上限 | 无限增长 | 默认 2000 条，超出淘汰最旧 |
| 导入重复编号 | 逐条询问覆盖/跳过/取消 | 导入前统一选择策略 |
| 数据文件 | 位于当前工作目录 | 位于可执行文件所在目录 |
| 旧数据文件 | 只能读 WHv1 | 读 WHv1 后自动升级为 WHv2 |

> 注意：v1 与 v2 的数据文件格式不同（WHv1 / WHv2），但 v2 **可直接读取 v1 的数据文件**并自动迁移。
> 反向不支持——这是刻意设计，避免"新格式被旧程序写坏"。

## 八、为什么保留 v1

1. **对照基线**。所有性能数字都需要一个"改造前"的参照物，v1 就是这个参照物。删掉它，v2 的加速比就成了无根之木。
2. **展示演进过程**。同一套业务语义如何从"能跑"变成"跑得快"，这个过程比结果更有说服力。
3. **失败清单**。v1 的每个缺陷都可以在 v2 的 [04-engineering-notes.md](04-engineering-notes.md) 里找到根因分析与修复方式，
   形成"发现问题 → 分析原因 → 验证修复"的完整闭环。
4. **诚实**。项目从课程作业起步，没必要隐藏起点。
