## 一、测试口径

| 项 | 说明 |
|---|---|
| **基线（v1）** | 忠实还原 v1 的实现方式：`std::vector` 承载数据 + `for` 循环线性查找 + 无索引 |
| **对照（v2）** | 哈希表主索引 + AVL 有序索引 + 自适应匹配器 |
| 编译器 | MSVC 19.51，`x64`，`/O2` |
| 计时 | `std::chrono::steady_clock`，只统计核心循环，排除数据生成与容器构造 |
| 防优化 | 每项结果累加到 `volatile` 校验和并回显，避免编译器消除被测代码 |
| 硬件 | 13th Gen Intel Core i9 / 32 GB RAM / Windows 11 |

### 关于数据波动

同一台机器多次运行，绝对值会有 **±30% 左右**的波动（受后台负载、CPU 频率、缓存状态影响），
但**量级与趋势稳定**。本页数据取自同一次完整运行，保证各项之间可比。如有疑义，请在本机重跑。

## 三、逐项分析

### 1. 按编号查询

三组测试刻意设计成**线性扫描的总工作量相近**（约 `2×10⁸` 次比较），只改变数据规模与查询次数：

| N | 查询次数 | 线性扫描总比较次数 | v1 总耗时 | v2 总耗时 |
|---|---|---|---|---|
| 1,000 | 200,000 | 2×10⁸ | 27.6 ms | 0.98 ms |
| 10,000 | 20,000 | 2×10⁸ | 29.5 ms | 0.26 ms |
| 100,000 | 2,000 | 2×10⁸ | 79.5 ms | 0.022 ms |

**结论**：v1 的耗时随 N 线性上升；v2 的单次耗时稳定在 **5~13 ns**（与 N 无关）。
加速比从 28× 涨到 3579×，正是 `O(n)` 与 `O(1)` 的差距随规模放大的直观体现。

单次查询 ≈ 11 ns 这个量级，也符合一次哈希计算 + 一次内存随机访问的物理成本。

### 2. 构建索引

v1 在追加前需要遍历已有记录判重，整体 `O(n²)`；v2 用哈希表判重 `O(n)`。

| N | v1 | v2 | 加速比 |
|---|---|---|---|
| 5,000 | 4.19 ms | 0.55 ms | 7.6× |
| 20,000 | 63.7 ms | 2.45 ms | 26.0× |

**结论**：加速比随 N 增长而变大，符合 `O(n²)` 与 `O(n)` 的比值趋势。
v2 单条插入成本约 110~123 ns，主要开销是 AVL 两次插入的旋转与 `std::string` 拷贝。

### 3. 有序输出

这是最有信息量的一组。四种方案对照（基线 = `std::sort` 直接排序元素）：

| 方案 | N=50,000 | N=200,000 | 说明 |
|---|---|---|---|
| `std::sort` 排序元素 | 7.11 ms | 42.57 ms | 基线 |
| 手写快排 · 排下标 | 4.45 ms (**1.60×**) | 27.35 ms (**1.56×**) | 快于 `std::sort` |
| 手写归并 · 排下标 | 6.30 ms (1.13×) | 37.60 ms (1.13×) | 稳定排序，略慢 |
| 手写堆排 · 排下标 | 7.07 ms (1.00×) | 154.40 ms (**0.28×**) | 随规模急剧恶化 |
| **AVL 中序** | **0.66 ms (10.74×)** | **4.82 ms (8.83×)** | 索引化排序 |

三个结论：

1. **排序下标比排序元素快约 1.6 倍**。`Item` 内含 `std::string`（32 字节以上），
   直接排序会产生大量大对象搬移；排下标只交换 8 字节整数，最后按下标取回。
2. **AVL 中序把"排序"从 `O(n log n)` 降成 `O(n)`**。因为中序遍历本身就是有序序列，
   每次排序不必重新比较。代价是一次性建树成本（N=20 万时 136 ms），
   所以**排序次数越多越划算**——这是典型的"空间/预计算换时间"。
3. **堆排在大规模下崩掉（0.28×）**。堆排是跳跃式访问，缓存局部性差；
   数据量增大后 cache miss 成为主导因素，理论上的 `O(n log n)` 优势被常数惩罚吃掉。

> 说明：手写快排能快过 `std::sort`，是因为比较的是"下标 + 外部数组"而非"元素本身"，
> 并非算法优于 introsort。若同样排元素，手写快排会略慢于 `std::sort`。

### 4. 价格区间查询

| N | 查询次数 | v1 | v2 | 加速比 |
|---|---|---|---|---|
| 10,000 | 500 | 13.5 ms | 1.10 ms | 12.2× |
| 100,000 | 200 | 57.9 ms | 14.5 ms | 4.0× |

**为什么规模变大后加速比反而下降**：区间宽度固定为 40 元，但价格范围是 1~999 元。
N 从 1 万涨到 10 万，落在区间内的命中数 `k` 同比例增长，
`O(log n + k)` 中的 `k` 项逐渐主导，而 v1 的 `O(n)` 也因为同样的命中而"没变慢那么多"。
这正是范围查询的固有特性：**当命中集占比很大时，任何索引都退化为全扫描**。

### 5. 字符串匹配

| 场景 | 朴素 | 自适应匹配器 | 结论 |
|---|---|---|---|
| 真实商品名（约 6 字节模式） | 6.62 ms | 7.58 ms | **0.9×，基本持平** |
| 最坏情况（20 KB 文本 + 1 KB 高重复模式） | 32.3 ms | 0.109 ms | **295×** |

这是本项目最值得记录的一次**反向优化**：

- 最初直接用 KMP 替换朴素匹配，实测反而慢了 3.5 倍——每次调用都重建 lps 数组，
  又给每段文本拷贝一份小写副本，堆分配开销完全盖过算法优势。
- 修正为"模式预编译一次 + 大小写折叠下沉到编译期"后，短模式仍有约 10% 的常数劣势。
- 最终实现**按模式长度自适应**：短于 8 字节走朴素，否则走 KMP。

所以第 5a 项的 0.9× 不是失败，而是**刻意保留的正确取舍**：短模式用朴素更快，
长模式用 KMP 快两个数量级，两者兼顾。

### 6. AVL 树高

| N | 100 | 1,000 | 10,000 | 100,000 |
|---|---|---|---|---|
| AVL 树高 | 7 | 10 | 14 | **17** |
| `log₂(N)` | 6.64 | 9.97 | 13.29 | 16.61 |
| 普通 BST（顺序插入） | 100 | 1,000 | 10,000 | 100,000 |

顺序插入是最恶劣的输入（普通 BST 完全退化为链表）。AVL 的高度稳定贴近
理论下界 `1.44·log₂(N+2)`，证明旋转策略与高度维护是正确的。

## 四、总结

| 优化点 | 收益量级 | 代价 |
|---|---|---|
| 哈希表主索引 | 查询 **10³ 量级**提升 | 额外 `O(n)` 内存；需维护一致性 |
| AVL 有序索引 | 排序 **6~11×**，区间查询 **4~12×** | 一次建树 `O(n log n)`；写操作多两次 `O(log n)` |
| 排序下标而非元素 | **1.6×** | 需额外 `O(n)` 下标数组 |
| 自适应 KMP | 最坏 **300×**，常见场景持平 | 一个阈值常量 |

**核心判断**：所有优化都建立在"先测、再改、再测"之上。
其中第 5 项的两次修正（KMP 反而变慢、短模式自适应）说明——
**理论复杂度更优不等于实际更快，必须用数据说话**。
